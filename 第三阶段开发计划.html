第三阶段开发计划
最小完整冒险流程（已完成）

在第二阶段已经完成的数据驱动单场战斗之上，建立一条具有“开始、选择、战斗、成长、终点”的完整游戏流程。 本阶段不追求大量动画和最终美术，而是优先证明：现有战斗系统能够真正成为一局游戏中的可重复环节。

计划版本 v0.3 制定日期 2026-08-26 完成日期 2026-09-04 前置版本 v0.2 已完成 Godot 4.6
阶段唯一目标： 玩家能够从主菜单开始一局冒险，在一张三节点地图上依次经历普通战斗、休整与 Boss 战； 战斗之间保留生命与牌组成长，最后进入胜利或失败结算，并能返回主菜单重新开始。

01 · Current Baseline

第三阶段开始时项目已经具备什么

第三阶段没有推翻已有战斗系统。阶段开始时，项目已经完成“用资源描述战斗内容、用运行时状态执行一场战斗”的基本分层， 当时缺少的是战斗之外的局内流程；这一缺口现已由 RunState 与 GameFlowController 补齐。

已具备：静态战斗内容

  • CardDefinition 描述卡牌。
  • CombatEffectDefinition 描述伤害、防御、抽牌等效果。
  • CombatantDefinition 与 EnemyDefinition 描述角色和敌人。
  • EncounterDefinition 描述当前的一场遭遇。

已具备：单场战斗运行时

  • BattleState 管理能量、回合、手牌与牌堆。
  • CombatantState 管理当前生命与格挡。
  • EnemyState 管理固定行动循环。
  • CardInstance 表示一场战斗中的卡牌实例。

已具备：战斗编排与界面

  • BattleController 连接状态、视图与行动队列。
  • ActionQueue 依次执行卡牌与敌人效果。
  • 卡牌、玩家、敌人的视图只负责显示与输入。
  • 已有 6 张卡牌、2 名敌人、2 场遭遇。
第三阶段开始前的限制（现已解决）： main.tscn 直接进入 battle.tscn； BattleController 在自身准备完成后自动开始检查器中绑定的遭遇； 战斗结束只能重新开始同一场战斗。当时项目还没有“这一局冒险”的拥有者。
02 · Goal & Scope

第三阶段已经达成的目标

衡量本阶段是否成功，不看动画数量，也不看地图是否随机生成，而看玩家是否能从头到尾走完一局短小但完整的冒险。

本阶段已完成

  • 主菜单与“开始游戏”。
  • 一张可显示节点状态的三节点地图。
  • 从地图节点进入不同遭遇。
  • 玩家生命跨战斗保留。
  • 普通战斗胜利后连续进行 3 轮奖励，每轮从 3 张卡中选择 1 张加入牌组。
  • 休整节点恢复生命。
  • Boss 胜利、战斗失败、返回主菜单与重新开始。
  • 静态资源、局内状态、单场战斗状态的职责清晰。

本阶段明确不做

  • 随机或程序化地图生成。
  • 商店、事件、遗物、药水、货币。
  • 存档、读档、局外成长。
  • 多敌人、复杂选定目标、状态效果体系。
  • 正式的异步战斗演出与完整动画管线。
  • 最终美术、音效与复杂 UI 装饰。
界面策略： 地图节点、主菜单和结算页可以先使用简单按钮、文字与颜色； 奖励选择使用以 Button 为根节点的独立卡牌组件。 只要信息清楚、操作正确、流程完整，就达到本阶段目标。视觉打磨留给后续阶段。

节点状态

地图不是三个普通按钮

每个节点至少要有 锁定、可进入、已完成 三种状态。 初始只允许点击第一个节点，完成当前节点后才解锁下一个节点。

跨战斗成长

生命和牌组会延续

战斗结束后保留剩余生命；奖励卡加入本局牌组，并在下一场战斗中出现。 格挡、能量、抽牌堆和敌人行动不跨战斗保留。

明确终点

一局必须能够结束

任意战斗失败立即进入失败结算；Boss 胜利进入胜利结算。 结算页点击再次启程后返回主菜单并清理旧状态；再次点击开始时创建全新的局内状态。

04 · Architecture

架构演进：增加“局内层”，不污染战斗层

第二阶段只有“静态定义 → 单场战斗状态 → 战斗视图”。 第三阶段在战斗外增加一层 Run，专门拥有整局冒险持续存在的数据与页面流程。

RunState：整局冒险的真相

  • 玩家当前生命。
  • 本局拥有的卡牌定义列表。
  • 当前、可进入、已完成的地图节点。
  • 本局状态：进行中、胜利或失败。
战斗开始时复制进入 ⇄ 战斗结束时只回写结果

BattleState：单场战斗的真相

  • 战斗中的玩家与敌人状态。
  • 能量、回合与阶段。
  • 抽牌堆、手牌、弃牌堆。
  • 本场战斗创建的 CardInstance。
层级 核心对象 负责什么 不应该负责什么
静态定义层 RunDefinition、MapDefinition、MapNodeDefinition 描述默认开局、地图拓扑、节点内容、奖励池。 当前生命、已完成节点、随机出的奖励结果。
局内运行时层 RunState 保存一局冒险跨场景持续的数据并执行局内规则。 具体界面节点、战斗按钮、单场能量和牌堆。
流程编排层 GameFlowController 切换页面，连接地图、战斗、奖励与结算。 直接修改卡牌资源或复制战斗规则。
单场战斗层 BattleController、BattleState 接收战斗输入，执行一场战斗并报告结果。 决定下一张地图、发奖励、保存整局牌组。
视图层 菜单、地图、奖励、结算、现有战斗视图 显示数据，收集输入，通过信号报告意图。 绕过状态对象直接改变游戏规则。
最重要的边界： 战斗进行期间，玩家生命以 BattleState.player_state 为准； 战斗结束时由流程控制器把剩余生命回写到 RunState，且只回写一次。 两个状态对象不能在战斗过程中互相实时同步，否则会产生两个真相源。
05 · Data Model

实际新增的静态数据与运行时状态

MapNodeDefinition

描述一个固定地图节点，是静态 Resource。

实际变量

  • enum NodeType { BATTLE, REST, BOSS }
  • node_id:String
  • display_name:String
  • node_type:NodeType
  • map_position:Vector2
  • next_node_ids:Array[String]
  • encounter_definition:EncounterDefinition
  • heal_amount:int

实际方法

  • is_invalid() -> bool
  • requires_encounter() -> bool

战斗与 Boss 节点必须提供遭遇；休整节点必须提供正数治疗量。

MapDefinition

描述整张固定地图及其连接关系，是静态 Resource。

实际变量

  • map_id:String
  • nodes:Array[MapNodeDefinition]
  • starting_node_ids:Array[String]

实际方法

  • is_invalid() -> bool
  • get_node_by_id(node_id:String) -> MapNodeDefinition
  • has_node(node_id:String) -> bool

验证节点 ID 唯一、连接目标存在、无自连接、起点存在、至少有一个 Boss，且示例节点都能从起点到达。

RunDefinition

描述一局冒险的默认配置，是静态 Resource。

实际变量

  • run_id:String
  • player_definition:CombatantDefinition
  • starting_deck_entries:Array[DeckEntryDefinition]
  • map_definition:MapDefinition
  • reward_pool:Array[CardDefinition]
  • reward_option_count:int = 3
  • reward_selection_count:int = 3

实际方法

  • is_invalid() -> bool

奖励池中的卡牌 ID 应唯一，且可用奖励数量不得少于一次展示数量。

RunState

保存一局冒险真正变化的数据，是纯运行时 RefCounted。

实际变量

  • enum RunStatus { SETUP, IN_PROGRESS, VICTORY, DEFEAT }
  • definition:RunDefinition
  • current_health:int
  • owned_cards:Array[CardDefinition]
  • current_node_id:String
  • available_node_ids:Array[String]
  • completed_node_ids:Array[String]
  • status:RunStatus

实际方法

  • run_state_init(new_definition:RunDefinition) -> bool
  • is_invalid() -> bool
  • can_enter_node(node_id:String) -> bool
  • enter_node(node_id:String) -> bool
  • complete_current_node() -> bool
  • add_card(card_definition:CardDefinition) -> bool
  • heal(amount:int) -> int
  • mark_victory() -> bool、mark_defeat() -> bool
牌组存储规则： RunState.owned_cards 中每个数组元素代表玩家实际拥有的一张卡，允许同一卡牌定义出现多次。 它只保存只读的 CardDefinition 引用，不保存 CardInstance。 每次进入战斗时，才根据该数组重新创建本场战斗专用的卡牌实例。
静态资源不可被运行时修改： 获得奖励卡时只向 RunState.owned_cards 追加引用； 不允许改变 RunDefinition.starting_deck_entries、DeckEntryDefinition.count 或任何 CardDefinition 字段。

BattleController 的外部契约

战斗控制器继续负责一场战斗，但不再决定整局流程。

新增信号

signal battle_finished(
    victory:bool,
    remaining_player_health:int
)

新增公共入口

func start_battle(
    encounter:EncounterDefinition,
    player_definition:CombatantDefinition,
    deck_definitions:Array[CardDefinition],
    starting_player_health:int
) -> bool

此方法验证输入、创建新的战斗状态、为牌组中的每个卡牌定义创建一个新 CardInstance， 再刷新界面并开始玩家回合。

MapView 与 MapNodeView

位于视图层，只把地图状态呈现为可理解、可点击的界面。

MapView

  • signal node_selected(node_id:String)
  • setup(new_map_definition:MapDefinition, new_run_state:RunState) -> bool
  • refresh_map() -> bool

MapNodeView

  • signal pressed(node_id:String)
  • setup(new_node_definition:MapNodeDefinition, new_state:int) -> bool
  • set_interactable(enabled:bool)

连线由 next_node_ids 和 map_position 决定； 按钮是否可点由 RunState.can_enter_node() 决定。

RewardCardView、RewardView 与结算页面

RewardCardView

  • signal reward_card_selected(card_definition:CardDefinition)
  • setup(new_card_definition:CardDefinition) -> bool
  • set_interactable(enabled:bool)
  • 根节点使用 Button，负责展示卡牌名称、基础费用、插画和描述，并呈现悬停、按下与禁用状态。

RewardView

  • signal reward_selected(card_definition:CardDefinition)
  • setup(new_options:Array[CardDefinition]) -> bool
  • 根据候选数据实例化多个 RewardCardView；首次选择后禁用全部奖励卡并只发出一次信号。

MainMenu / RunResult

  • 主菜单发出 start_requested。
  • 结算页通过 setup(victory:bool) 接收胜负状态，发出 restart_requested 请求返回主菜单。
  • victory == true：“恭喜，强敌已被战胜，你的旅途还在继续！”
  • victory == false：“遭遇强敌落败，旅程暂时告一段落...”

RewardCardView 直接读取 CardDefinition，不创建假的 CardInstance， 也不继承或复用包含战斗交互逻辑的 CardView；RewardView 只负责管理整组奖励卡和上报最终选择。

流程控制器的页面原则： page_container 中同时只保留一个活动页面。 切换页面时先实例化并验证新页面，成功后再移除旧页面、挂载新页面并连接信号；同一个页面实例只报告一次选择，防止重复发奖、重复结算或重复进入节点。
08 · Minimum Content

第一条完整冒险的固定内容

节点 1

普通战斗

  • 遭遇：cave_crawler_encounter.tres
  • 当前对应敌人显示名：哥布林战士。
  • 胜利：保留剩余生命，进入卡牌奖励。
  • 失败：直接进入失败结算。
节点 2

休整

  • 治疗量：15。
  • 治疗后生命不超过玩家最大生命。
  • 完成后直接返回地图。
  • 不需要单独制作复杂休整场景。
节点 3

Boss 战

  • 遭遇：ruin_guard_encounter.tres
  • 胜利：整局冒险胜利，不再发普通卡牌奖励。
  • 失败：进入失败结算。
  • 该节点没有后继节点。
默认局内配置 内容 原因
玩家 combatants/data/player.tres，最大生命 50。 直接复用第二阶段已经验收的玩家定义。
初始牌组 5 张打击、5 张防御。 容易观察奖励卡是否真的进入下一场战斗。
奖励池 双重打击、防守反击、战术防御、重击。 复用 4 张进阶卡，覆盖重复伤害、混合效果、抽牌和高费用伤害。
奖励数量 连续进行 3 轮奖励，每轮随机展示 3 张不同卡并选择 1 张。 一场普通战斗共获得 3 张卡，同时避免同一奖励页重复选项。
地图结构 普通战斗 → 休整 → Boss 的固定线性三节点；当前横坐标依次为 220、491、762。 数据结构支持连接关系，但首个样例不引入分支与随机生成复杂度。
09 · Development Order

实际采用的开发顺序

以下顺序按照依赖关系排列：先建立可验证的数据，再建立局内状态，最后接入页面与战斗。 每一步只解决一个明确问题，完成后再进入下一步。

A. 静态数据基础
01

创建地图节点定义

文件：run/map/data/map_node_definition.gd 层：静态定义层

实现 NodeType、节点身份、位置、后继节点、遭遇与治疗字段，并让 is_invalid() 根据节点类型执行条件验证。

  • 战斗与 Boss 节点缺少遭遇时非法。
  • 休整节点治疗量不为正数时非法。
  • 节点 ID 与显示名为空时非法。
02

创建地图定义

文件：run/map/data/map_definition.gd 层：静态定义层

集中保存节点数组与起点，并提供按 ID 查找节点的唯一入口。 使用两阶段验证：先验证节点自身与唯一 ID，再验证连接引用和可达性。

  • 重复 ID、缺失连接目标、自连接、无起点或无 Boss 均不可通过。
  • get_node_by_id() 找不到时返回 null。
  • 示例地图中的所有节点均可从起点到达。
03

制作三节点地图资源

文件：run/map/data/first_map.tres 层：静态内容资源

创建普通战斗、休整、Boss 三个子资源，按线性关系连接，并绑定现有两份遭遇资源。 map_position 使用清晰的横向或纵向坐标，供地图视图直接布局。

04

创建整局定义与默认冒险资源

文件：run/data/run_definition.gd 资源：run/data/default_run.tres 层：静态定义层

把玩家、初始牌组、地图、奖励池和奖励数量组织成一份默认冒险配置。 开局仍使用 5 张打击与 5 张防御，奖励池使用已有 4 张进阶卡。

B. 局内运行时核心
05

实现 RunState

文件：run/model/run_state.gd 层：局内运行时层

初始化时复制玩家满生命，把每个 DeckEntryDefinition.count 展开为独立的卡牌定义引用， 再复制地图起点为可进入节点。节点进入、完成、治疗、加卡和胜负状态都只能通过它的方法改变。

  • 不能进入锁定、已完成或不存在的节点。
  • 同一时刻最多有一个当前节点。
  • 完成节点后移入已完成列表，并解锁合法后继节点。
  • 治疗返回实际恢复量，且不能超过最大生命。
  • 失败或胜利后不允许继续进入节点。

10 · Design Decisions

本阶段提前确定的关键设计决定

1. 不使用 Autoload 保存 RunState

main.tscn 在整局游戏中持续存在，GameFlowController 可以自然持有 RunState。返回主菜单时释放旧状态，当前规模不需要引入全局单例。

2. 地图数据支持连接，首个样例保持线性

next_node_ids 为未来分支留出空间，但第三阶段的固定三节点地图不做路线选择。 先验证流程闭环，再增加地图生成和分支规则。

3. RunState 保存 CardDefinition，不保存 CardInstance

CardInstance 的费用和所在牌堆都属于单场战斗。 跨战斗只需要保存“拥有哪几张卡”；下一场战斗应创建全新的实例。

4. BattleController 不知道地图与奖励

它只接收战斗输入并报告结果。这样未来即使从事件、教程或 Boss 门进入战斗， 也可以复用同一个战斗模块，而无需在其中添加大量流程分支。

5. 奖励展示使用独立的 RewardCardView

战斗卡牌视图包含可打出状态、战斗实例和点击逻辑。 奖励卡可参考或复制战斗卡牌的视觉布局，但不继承战斗视图脚本；它以 Button 为根节点，只读取静态的 CardDefinition 并报告选择。 RewardView 再组合多张 RewardCardView，负责整组选项的生成、锁定和信号汇总，从而保持单卡展示与页面编排的职责边界。

6. 战斗演出不是第三阶段前置条件

现有同步行动队列足以支撑流程验证。本阶段不为了等待动画而重构异步队列； 等完整循环成立后，再根据真实界面需求设计演出系统。

11 · Risks

最容易出错的地方与预防方式

风险 可能表现 预防方式
生命有两个真相源 地图显示的生命与战斗生命不一致，或重复结算伤害。 开战复制一次，结算回写一次；战斗过程中只认 BattleState。
运行时修改静态资源 重新开局后初始牌组变多，或者资源在编辑器中被污染。 RunState 使用自己的数组；只保存资源引用，不改资源字段。
重复信号连接 点击一次获得两张奖励、完成两个节点或弹出两个页面。 始终只有一个活动页面；切换时释放旧页面；结果回调设置一次性防护。
旧自启动与新流程并存 战斗创建后自动启动检查器遭遇，又被流程启动一次。 新流程接通后删除固定 encounter 绑定、_ready() 中的自启动战斗逻辑与旧重开入口。
地图节点重复点击 连续创建多个战斗页面或多次治疗。 视图先禁用按钮，流程层再调用 RunState.can_enter_node() 二次验证。
奖励页出现重复卡牌 三项中有相同定义，选择感变弱。 验证奖励池 ID 唯一，并从池中无放回抽取。
重新开始残留旧状态 上一局牌组、生命或完成节点带入新局。 返回主菜单时释放旧状态；再次开始时新建 RunState，不复用旧状态对象。
12 · Acceptance

第三阶段最终验收标准

以下项目已经全部通过，第三阶段完成。界面仍是原型，但流程和状态边界不依赖人工跳转或临时改检查器资源。

玩家流程验收

  • 启动游戏先看到主菜单，点击后创建一局全新冒险。
  • 地图同时显示三个节点及其连接，初始只允许进入第一个节点。
  • 点击普通战斗节点后，进入该节点绑定的遭遇。
  • 普通战斗胜利后连续显示 3 轮卡牌奖励，每轮从 3 张不同卡牌中选择 1 张。
  • 奖励卡会加入牌组，并可能在下一场战斗中抽到。
  • 战斗剩余生命返回地图后保留。
  • 休整节点恢复 15 点生命，且不超过最大生命。
  • 完成前一个节点后解锁下一个，完成节点不能再次进入。
  • Boss 胜利进入胜利结算，任意战斗失败进入失败结算。
  • 结算页点击再次启程后返回主菜单；重新开始时生命、牌组和地图进度全部恢复默认。

架构与数据验收

  • RunState 是战斗外生命、牌组和地图进度的唯一真相源。
  • BattleState 仍是单场能量、回合、牌堆和战斗角色的唯一真相源。
  • BattleController 不引用 RunState，只接收输入并报告结果。
  • 地图、奖励和菜单视图不直接修改游戏状态。
  • 运行时不会改变任何 .tres 静态资源字段。
  • 每场战斗都从局内牌组创建新的 CardInstance。
  • EncounterDefinition 不再与 RunDefinition 重复拥有玩家和牌组。
  • 旧的固定遭遇自启动与原地重开入口已被清理。
  • 现有 6 张卡牌、2 名敌人及其效果顺序仍保持原有行为。
  • README 已更新到 v0.3，并能说明如何更换地图、节点遭遇与奖励池。
验收结果： 不需要修改检查器中的遭遇资源，不需要手动切换场景，也不需要开发者介入； 玩家已经通过界面完成从“开始”到“胜利或失败”的完整试玩，并验证可以返回主菜单再开始一局干净的新冒险。
13 · Resulting Foundation

第三阶段结束后，项目已经具备的基础

第三阶段完成后，项目第一次拥有真正的“游戏骨架”： 静态资源可以定义一局冒险，RunState 可以保存跨战斗进度， GameFlowController 可以编排页面，而现有战斗模块可以被任意节点调用。
